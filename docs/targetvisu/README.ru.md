# OpenPLC TargetVisu — Editor 0.1.0

Первый этап TargetVisu: редактор экранов внутри OpenPLC Editor 4.3.3.
Предназначен для последующего нативного клиента GTK/Cairo с выводом через X11.
Это редактор и локальная симуляция интерфейса. Клиент GTK/Cairo и связь
визуализации с работающим ПЛК в данный выпуск не входят.

Включена предыдущая доработка Editor для диагностики Modbus. Runtime 0.2.1
на Banana Pi для работы над экранами менять не требуется.

## Быстрый запуск на Windows

В полном архиве находится папка editor-source. Требуются Git, Node.js 22.x x64
и npm >= 10. Открыть CMD в editor-source:

```cmd
npm ci
npm run dev
```

Штатный postinstall загружает strucpp и зависимости Electron. Откроется Editor
в режиме разработки. Создать или открыть обычный PLC-проект. В дереве проекта
выбрать **TargetVisu (X11)** рядом с Resource.

Для EXE-установщика штатная команда:

```cmd
npm run package
```

Результат упаковки: release\build. Упаковка и запуск Windows EXE здесь не
проверены. Для проверки компиляции в этой среде успешно использованы:

```cmd
npm run build:main
npm run build:renderer -- --no-devtool --no-optimization-minimize
```

Это production-конфигурация JavaScript без source maps и минимизации интерфейса.
Проверка компиляции не заменяет проверку Electron на Windows.

## Обновление исходников вместо полного архива

Небольшой архив Update содержит install_editor.py, overlay и targetvisu.patch.
Он рассчитан на editor-source из ранее выданного пакета Modbus Diagnostics 0.2.0.
Из каталога распакованного Update выполнить:

```cmd
py -3 install_editor.py --editor "D:\Project_PLC\editor-source" --check
py -3 install_editor.py --editor "D:\Project_PLC\editor-source"
```

Закрыть запущенный Editor перед заменой файлов. Установщик проверяет исходники,
допускает различие LF/CRLF и сохраняет резервную копию изменяемых файлов.
Неизвестные пользовательские изменения не перезаписываются. Если проверка
не проходит, использовать полный editor-source в отдельной папке либо перенести
патч вручную. Принудительной замены в установщике нет.
После обновления выполнить npm ci и npm run dev.

## Редактирование

1. Нажать **Create screen** или **+ Screen**. По умолчанию экран 800 × 480.
2. В панели Primitives добавить rectangle, ellipse, line, text, indicator,
   button или number.
3. Выбрать элемент на рабочем поле или в Layers. Перетаскивать мышью;
   нижняя правая синяя ручка меняет размер. Координаты и размеры можно ввести
   справа. Числовые свойства подтверждаются Enter или выходом из поля.
4. Shift/Ctrl + щелчок — множественное выделение; стрелки — сдвиг на 1 пиксель,
   Shift + стрелки — на шаг сетки. Поддержаны Grid и масштаб 50–200%.
5. Duplicate, Delete, To front/back и Align left/top/right/bottom управляют
   выделенными элементами. Ctrl+C/V копирует внутри редактора визуализации.
6. Undo/Redo, Ctrl+Z, Ctrl+Shift+Z или Ctrl+Y отменяют изменения. Одно
   перетаскивание — один шаг Undo. История хранится в памяти текущего окна.
7. Щелчок по пустому полю снимает выделение и открывает свойства экрана:
   имя, разрешение, фон, сетка и период будущего обновления Runtime.
8. Звезда отмечает стартовый экран. Поддержаны копирование и удаление экранов.

Имя экрана — латинский IEC-подобный идентификатор до 64 символов. Элементы
имеют отдельные UUID; порядок в elements задаёт порядок от заднего к переднему.
Линия поддерживает горизонтальное, вертикальное и два диагональных направления.
В первой версии нет групп-контейнеров, произвольного поворота и изображений.

## Привязки и действия

Переменные выбираются из проекта. Для программы используется имя экземпляра
из Resource, например Pump1.Pressure, а не имя типа программы main.
Глобальные переменные доступны по имени, GVL — как ListName.Variable.
Поддержаны скалярные BOOL, числовые типы, STRING и WSTRING. TEMP и ссылки
VAR_EXTERNAL не создают отдельные экземпляры переменных визуализации.
Структуры, массивы, вложенные экземпляры FB и библиотечные типы пока не раскрываются.

- Value variable — значение для текста, индикатора или числового поля.
- Visible when TRUE / Enabled when TRUE — BOOL-условия видимости и доступности.
- Цвет, активный цвет индикатора, обводка, цвет и размер текста — свойства элемента.
- Кнопка: set, toggle или momentary. Числовое поле: write с границами Minimum/Maximum.

Входы %I (включая разрешённые редактором адресные алиасы), CONSTANT и константные
GVL не предлагаются как цели записи. Проверяются существование, базовый тип и
совместимость действия. При удалении или переименовании переменной появляется
ошибка привязки; автоматического переименования всех ссылок пока нет.

Рабочий проект можно сохранить с незавершённой привязкой. Экспорт JSON
блокируется до исправления ошибок, чтобы не выдавать его как согласованный экран.

## Предпросмотр

Preview использует только локальные тестовые значения. Справа можно менять
числа и BOOL, проверять видимость, цвета и кнопки. Ввод уставки демонстрируется
в правой панели Input, а не в нативном GTK-виджете.

Предпросмотр **не исполняет ST** и не подключается к Runtime. Поэтому StartRequest
и Running в примере независимы: нажатие START меняет команду, но не рассчитывает
выход Running. Для проверки индикатора нужно отдельно изменить Running.
Momentary сбрасывается при отпускании, отмене указателя, смене экрана и выходе
из предпросмотра. Это локальное поведение, не реализованный сетевой механизм.

## Сохранение и обмен

Ctrl+S и Save Project сохраняют экраны в data.targetVisu файла project.json.
Работают повторное открытие проекта и восстановление снимка экрана при отказе
от сохранения вкладки. Сохранение визуализации использует общий project.json,
как Resource; оно может включать текущие изменения других данных в этом файле.

Export JSON создаёт отдельный targetvisu.json. Import JSON заменяет весь набор
экранов после подтверждения; текущая визуализация не изменяется при ошибке JSON.
Лимит импорта — 4 MiB, до 64 экранов, до 1000 элементов на экран.

Использовать для таких проектов именно эту модифицированную сборку. Обычный
Editor ещё не знает data.targetVisu и может не сохранить это поле.

## Пример

В архив включены example.targetvisu.json и папка demo-project.
Открыть demo-project как проект Editor. В нём есть main, экземпляр Pump1,
четыре переменные и готовый экран с давлением, состоянием и кнопками.
Для изучения экрана запускать или загружать ПЛК не требуется.

## Следующий этап: Runtime

Добавить отдельный процесс GTK/Cairo, загрузку JSON, разрешение символов по
карте текущей программы, обмен с ядром через Unix-сокет и обработку команд.
Сопоставление имён с адресами памяти при загрузке и контроль версии программы
пока не реализованы. В Runtime также понадобятся независимость графики от
цикла ПЛК и обработка потери клиента для momentary-команд.

Подготовленный JSON не содержит JavaScript или ST для исполнения. Действия
декларативные; backend Runtime должен повторно проверять тип и право записи.
